Both projects build on the work of the ToIP Decentralized Trust Graph
Working Group. They start from opposite ends. OpenVTC is built for
communities that meet online and can be joined from anywhere: a person's
keys live with an agent service, and a community runs as a service with
its own policy. RLTP is built for communities that meet in person and
often have no reachable server: keys stay on each device, and a group is
a place its members hold together.

This page describes OpenVTC as of October 2026. It is a young project
moving fast; where we are unsure, we say so.

## What we share

| | OpenVTC | RLTP |
|---|---|---|
| Credentials | DTG credential types: relationship (VRC), membership (VMC), invitation (VIC), and the newer authority credential (VAC) | Encounter credentials typed as DTG relationship credentials, invitations as DTG invitation credentials |
| Documents between parties | Every wire operation is bound to a versioned Trust Task | Every document between devices is a Trust Task document of a private type |
| Transport | DIDComm and TSP over a mediator, plus HTTP | A delivery adapter for the same mediator, being updated to TSP revision 3 |
| Identifiers | `did:key` for applications and members, `did:webvh` for agents, mediators, communities and rooms | `did:key` anchors per context |

## Where we build differently

### Where keys live

In OpenVTC's reference deployment, a person's master keys live in a
**Verifiable Trust Agent (VTA)**, a server that signs on request; private
keys never leave its process. It can be managed (the VTA Farm, the
recommended path) or self-hosted. The DTG specifications also describe
local agents on a person's own device, and a browser tab can now hold its
own key material as a member of a data room. We have not seen a complete
OpenVTC flow without a VTA.

In RLTP, keys stay on the person's devices. There is no agent service in
the path. In our current design work each device holds its own key in a
group, so a single lost device can be removed without removing the
person.

### What has to be reachable

In OpenVTC, joining a community, minting a persona and messaging go
through a VTA, a DID host and a mediator. Data rooms keep their records on
one host; reading and writing are calls to that host. The mediator queues
messages, so the recipient need not be online at the same time.

In RLTP, an encounter works without any network: two people scan each
other's codes, and the credentials travel later. A group's state is
replicated on every member's device. Members read and write offline, and
the replicas merge when they meet again. A relay or service is optional
and never decides alone.

### What a group is

OpenVTC has two kinds of group:

- A **Verifiable Trust Community (VTC)** is a community service running on
  a VTA. It admits members by policy and admin approval, keeps the member
  list and access control, issues and expires membership credentials, and
  publishes membership to an external trust registry. Communities can be
  members of other communities.
- A **data room** is a set of records for people and their AI agents,
  stored on a host and end-to-end encrypted with MLS. The room has its own
  `did:webvh`, which issues invitation, membership and authority
  credentials. One owner admits, removes and commits; the host accepts one
  epoch at a time.

An RLTP group is an encrypted document replicated on every member's
device, with a signed log of who joined, who left and which rules apply.
There is no owner and there are no admins: privileged operations need
what the group's own rule requires, for example two members. The log is
the only source of truth about membership, and a member is whoever holds
the key. Two removals made at the same time both take effect.

| | OpenVTC data room | RLTP group |
|---|---|---|
| Where the state lives | on one host, with optional read mirrors | on every member's device |
| Data | versioned records; CRDTs deliberately not adopted | any application data, merged as a CRDT |
| Who decides | one owner | the group's rule, no owner |
| Membership | MLS tree and credentials issued by the room | the signed log |
| Concurrent changes | one committer, one epoch at a time | concurrent removals both apply |
| Offline | reads of what was fetched; no offline writes | reads and writes |
| Identity | the room's `did:webvh` | the digest of the group's genesis |

## Where each design fits

OpenVTC fits communities that are open to people they have not met: a
community that admits by policy, recognises members of other communities,
publishes to a registry, and gives AI agents narrowly scoped authority.
Its private, zero-knowledge tier for rooms is planned.

RLTP fits communities whose members know each other and need to keep
working without a server: a camp, a festival, a neighbourhood, a
cooperative. The price is that RLTP has no path between strangers; that
is deliberate.

Many communities will need both. A neighbourhood group might run on RLTP
and still want to show an outside service that its members are real
people.

## Where they connect

The two worlds meet at a bridge. Statements cross it in both
directions; the grammar of checking stays where it came from.

<Bridge />

- **Encounter credentials as evidence.** OpenVTC's join and personhood
  policies evaluate credentials the operator admits. An RLTP encounter
  credential could be such evidence. Under the DTG's newer edge
  verifiability rule, it counts as a verified statement rather than an
  edge unless its issuer's community membership is shown; how a group
  without an issuer DID can serve as that anchor is an open question we
  have raised with the working group.
- **One transport.** Both use the same mediator. Our adapter was proven
  against an earlier mediator release and is being updated for TSP
  revision 3.
- **Ideas we would like to learn from.** The data rooms' epoch chain,
  which seals each old storage key under the new one so that a new member
  can read the history; verified reads, which let a member notice when a
  host withholds records; and the authority credential, which could let an
  RLTP group show membership to outsiders or delegate a narrow task to an
  agent.
- **Ideas that may be useful in return.** Offline writing with merge,
  concurrent removals without a sequencer, one key per device, and a
  group rule instead of an owner. The data rooms design itself names
  concurrent offline editing as the case that would reopen the CRDT
  question.

## Open questions

1. Is a complete OpenVTC flow without a VTA server planned, for example
   with an agent on the person's own device?
2. Which of the VTA custody levels keep the host from any access to keys?
3. Could a data room be served by a group rule instead of a single owner,
   for example through an authority credential the group issues by its
   own decision?
4. Would a VTC policy admit an RLTP encounter credential as personhood or
   join evidence, and in which form?
5. Can a group without an issuer DID, whose membership comes from a log,
   act as an anchor for edge verifiability?
